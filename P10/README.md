# Module Notes: FuncMage (Functional Programming — Lambdas, Higher-Order Functions, Closures, functools, Decorators)

Core theme: **functions as first-class citizens** — passed around, returned, combined, and wrapped, as an alternative/complement to the object-state-centric style of earlier OOP modules.

---

## Ex0 — Lambdas

- `lambda args: expression` — a nameless, single-expression function. No statements, no multi-line logic — just one expression that becomes the return value implicitly.
- Best fit: short, throwaway, single-use transformations passed directly as arguments to `sorted()`/`filter()`/`map()`. The moment logic needs a name, multiple statements, or reuse elsewhere, a regular `def` is the better, more maintainable choice.
- `sorted(iterable, key=lambda x: ..., reverse=True)` — the lambda returns *the value to sort by* per element, not a comparison. `reverse=True` for descending, separate from `key`.
- `filter(lambda x: ..., iterable)` — predicate function, keeps elements where truthy. Returns an **iterator**, not a list — wrap in `list(...)` if a list is required.
- `map(lambda x: ..., iterable)` — transforms every element. Same iterator-vs-list consideration as `filter`.
- `max(iterable, key=lambda x: ...)` / `min(...)` — same `key=` pattern as `sorted`, returns the *original element* with the extreme key value (not the key value itself) — index into it afterward if you need the underlying value (e.g. `max(mages, key=lambda m: m['power'])['power']`).
- **Real bug hit**: using `dict.get('power')` instead of `dict['power']` inside a `max`/`min` key lambda — `.get()`'s return type is `Any | None` (built for the "key might be missing" case), which broke type comparability under `mypy --strict`. Plain indexing is correct once you know the key is guaranteed present, and resolves the type ambiguity.
- **Contract-matching bug hit**: a function's `(rounded to 2 decimals)` requirement applies to what the *function itself* returns, not just what gets printed afterward. Rounding cosmetically at the print call site doesn't satisfy a spec describing the return value itself — round at the source, inside the function.
- A lambda referencing a variable from its enclosing function's scope (e.g. `filter(lambda x: x['power'] > min_power, mages)`, where `min_power` is `power_filter`'s own parameter) is already a closure — the formal closure concept from Ex2 shows up here first, informally.

## Ex1 — Higher-order functions

- A function that either **takes another function as an argument**, or **returns a function**, or both.
- Returning a function that itself matches the *same contract* as its inputs (same signature) is what enables **composability** — the output of one higher-order function can be fed right back into another, since nothing about the "shape" changed, only the behavior underneath.
- Pattern used throughout: outer function receives function(s) as arguments, defines an **inner function** that calls them (this inner function is a closure — it references `spell1`/`spell2`/`base_spell`/`multiplier`/etc. from the enclosing scope), then returns that inner function without calling it.
- **`Callable`** (type hint, from `collections.abc` — not `typing`, per this module's explicit guidance) vs. **`callable()`** (built-in function, runtime check of whether an object can actually be invoked with `()`) — related but distinct: one is static documentation of intent, the other is a runtime boolean check.
- **Real bug hit**: a decorator/wrapper silently ignoring one of its own parameters (`power_amplifier` hardcoding `* 3` instead of using its actual `multiplier` argument) — passes type checks and runs without error, but produces wrong behavior. A reminder that `mypy`/`flake8` catch type and style issues, never logic bugs — actually running and tracing through the output is the only way to catch this class of mistake.

## Ex2 — Closures and `nonlocal`

- A **closure**: an inner function that references a variable from its enclosing function's scope, and is then returned/used *after* the enclosing function has already finished executing — yet still "remembers" and can access that variable.
- **`nonlocal` is required only when *reassigning* a variable itself** (`count += 1` rebinds `count` to a new value) — not merely reading it, and not when mutating a mutable object's *contents* without rebinding the name itself.
  - **Required**: `mage_counter`, `spell_accumulator` — both do `nonlocal x; x += ...` (genuine reassignment).
  - **NOT required**: `enchantment_factory` (read-only closure, never modifies anything) and — the subtler case — `memory_vault`'s `store`/`recall` functions, which do `storage[key] = value` (mutating the dict's *contents*) without ever writing `storage = ...` (never reassigning the name `storage` itself to a different object).
- **Independent state, automatically**: each *separate call* to a closure-returning function (e.g. two calls to `mage_counter()`) creates a brand-new, separate execution of that outer function — meaning a brand-new, separate enclosing-scope variable each time. The two returned inner functions each only "remember" their own creation context, never sharing state with each other. This gives per-instance isolation without any class at all.
- **Why `nonlocal` is allowed but `global` is forbidden** (this module's own recurring evaluation question): `nonlocal` only ever reaches *one specific, already-known enclosing function's scope* — private to that one closure's own creation context, invisible to any other unrelated code in the program. `global` reaches shared, module-level state that *any* code anywhere could read or corrupt — exactly the kind of unpredictable shared mutable state functional style deliberately avoids.
- `dict.get(key, default)` — cleaner than `try/except KeyError` for "return a value, or a fallback if the key is missing" — a normal expected-miss case, not a truly exceptional one.

## Ex3 — `functools` and `operator`

- **`functools.reduce(function, iterable)`** — repeatedly applies a two-argument function cumulatively across a sequence, collapsing it to one value. More general than a specialized built-in like `sum()`, since the *combining function itself* is swappable (`add`, `mul`, a custom min/max lambda, anything) — this generality (not raw performance) is the actual point of `reduce`.
- **`operator` module** (`operator.add`, `operator.mul`, etc.) — pre-built two-argument functions matching Python's operators, meant to be passed **directly** to `reduce` rather than wrapped in a redundant lambda (`reduce(add, spells)`, not `reduce(lambda a, b: add(a, b), spells)` — the latter defeats the purpose of importing `operator` in the first place). `min`/`max`-style "pick the smaller/larger of two" isn't a literal operator, so a small lambda is the reasonable exception there.
- **Edge case ordering worth being deliberate about**: check "is the input empty" *before* attempting a lookup/operation that could itself fail for an unrelated reason (e.g. an unknown operation string) — so that an empty list always safely returns the documented fallback regardless of whatever else might also be wrong with the call.
- **`functools.partial(function, *fixed_args, **fixed_kwargs)`** — returns a new callable with some arguments pre-filled ("locked in"), leaving the rest for later. Keyword-based fixing (`power=50, element="fire"`) is generally clearer than positional when leaving a "gap" in the middle of a parameter list for a later argument.
- **`functools.lru_cache`** — decorator that caches a function's return values by input arguments, skipping recomputation on repeat calls with the same inputs (memoization). **Critical detail**: for a recursive function, the recursive calls must go through the *decorated* function itself (calling itself by its own decorated name) — not an undecorated helper — or caching only applies to the outermost call and none of the recursive sub-calls, defeating most of the benefit. `.cache_info()` exposes hit/miss/size stats to *prove* caching is happening, rather than just asserting it.
- **`functools.singledispatch`** — lets one function name behave differently based on the *type* of its first argument, via `@base_func.register` for each type, without manual `isinstance()` chains. The base (undecorated-by-register) function is the fallback for any type with no specific registration.
- **Testing-your-own-test bug hit**: testing a `singledispatch` fallback by calling it with a value of a *type that's actually registered* (a `str`, when `str` already had its own handler) — the output looked plausible, but was silently exercising the wrong code path entirely, never actually reaching the fallback. A reminder to verify a test genuinely exercises the intended path, not just that its output happens to look right.

## Ex4 — Decorators

- Structurally: a decorator is a **higher-order function** (Ex1) that internally uses a **closure** (Ex2) to remember the function it's wrapping — decorators are the natural convergence point of both earlier concepts.
- Basic shape: `def decorator(func): def wrapper(*args, **kwargs): ...; return func(*args, **kwargs) ...; return wrapper; return decorator`. `*args, **kwargs` matters specifically because a general-purpose decorator can't assume anything about the signature of whatever function it'll eventually wrap.
- **`functools.wraps(func)`** applied to the inner `wrapper` — without it, the wrapper silently replaces the original function's `__name__`/metadata. Not cosmetic: code that inspects `func.__name__` (e.g. to print "Casting {name}...") depends on this being preserved correctly.
- **Two-level vs. three-level nesting**: a plain decorator (`spell_timer`) needs only `decorator(func) -> wrapper`. A **decorator factory** — one that itself takes configuration (`min_power`, `max_attempts`) *before* knowing which function it'll wrap — needs a third outer layer: `factory(config) -> decorator(func) -> wrapper(*args, **kwargs)`. The configuration is captured by the middle layer as a closure, exactly like `spell_accumulator`'s `initial_power`.
- **Real bug hit, worth remembering as a category**: a wrapper referencing a bare name (`power`) that isn't one of its own parameters — Python doesn't error, it just silently resolves the name via the enclosing/global scope, which in this case was an unrelated **global variable** that happened to share the same name as an intended local concept. The output looked plausible purely by coincidence. The fix required deliberately extracting the value from the actual call arguments (`kwargs.get('power')`), which in turn required committing to a specific calling convention (callers must pass `power` as a keyword, not positionally) — since a generic `*args, **kwargs` wrapper has no way to know "which position is power" without an explicit rule.
- **A decorator applied directly to a function is that function now** — don't also pass the original function in again as an argument at call time (`validated_heal(heal, power=50)` was wrong; once `heal` was baked in via `power_validator(min_power)(heal)`, calling the result only ever needs the arguments `heal` itself expects: `validated_heal(power=50)`).
- **`@staticmethod`** — a method that needs neither `self` nor `cls`; effectively a plain function organized inside a class namespace for logical grouping, used when the logic doesn't depend on any particular instance or the class itself (e.g. validating a bare string, independent of any specific mage).
- Broad `except Exception:` inside a **retry** mechanism is a deliberate, correct design choice (the whole point is generic resilience to *any* failure) — different from the usual advice to catch narrow, specific exception types; context (a genuine catch-all recovery tool) determines whether broad catching is a smell or the intended behavior.

## General habits reinforced across this whole module

- `mypy`/`flake8` catch types and style — **never logic**. Several real bugs here (ignored parameters, wrong variable scope, mismatched test data) passed both cleanly while still being functionally wrong. Actually running the code and tracing the output against the expected behavior remains the only way to catch this category of mistake.
- When a function's own written contract specifies a property of its **return value** (e.g. "rounded to 2 decimals"), satisfy that inside the function itself — don't rely on external code (like a `print` call) to cosmetically paper over an internal value that doesn't actually meet the spec.
- Global variables were explicitly forbidden in this module's rules for good reason — the accidental-global-shadowing bug in `power_validator` is a concrete, first-hand illustration of exactly the kind of silent, hard-to-trace failure that rule exists to prevent.
